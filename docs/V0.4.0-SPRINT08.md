# zfetch v0.4.0 — Sprint 08: Linux Compatibility Candidate

Status: **Candidate. Do not tag or release 0.4.0 before all CI tests pass.**

This sprint does not bump `Cargo.toml` or publish any release. It preserves the
existing Arch build and Rust source, and replaces only the two packaging
workflows with baseline-constrained builders while adding a new static tarball
workflow.

## Packaging matrix

| Format | Build environment | GLIBC ceiling | Architectures | CI name |
| --- | --- | --- | --- | --- |
| .deb | Ubuntu 22.04 containers | 2.35 | amd64, arm64 | Debian package builds |
| .rpm | Rocky Linux 9 containers | 2.34 | x86_64, aarch64 | RPM and portable Linux builds |
| GNU .tar.gz | Rocky Linux 9 containers | 2.34 | x86_64, aarch64 | RPM and portable Linux builds |
| Static musl .tar.gz | Native Ubuntu runners, musl toolchain | No GLIBC dependency expected; CI enforces no NEEDED/INTERP | x86_64, aarch64 | Portable musl Linux builds |
| .pkg.tar.zst | Arch Linux rolling container | Native Arch dependency | x86_64 | Existing Arch Linux package |

On GNU builds, `packaging/check-glibc.sh` fails the CI job if the resulting
ELF requires a newer GLIBC version than its intended baseline.

## Why the additional static binary?

GNU tarballs and distro packages are dynamically linked and depend on runtime
libraries. The musl variant aims to support more systems without a GLIBC
requirement. It is NOT a guarantee of compatibility with every kernel, CPU,
or Linux distribution. The binary's Linux system detection remains dependent on
the actual environment and may lack services such as D-Bus inside containers.

## Manual test steps after GitHub Desktop Commit to main / Push origin

In GitHub > Actions, use `Run workflow` on the following:

1. Debian package builds
2. RPM and portable Linux builds
3. Portable musl Linux builds
4. Arch Linux package (unchanged; smoke test again near release)

Expected artifacts:

- `zfetch-deb-amd64`, `zfetch-deb-arm64`
- `zfetch-rpm-portable-x86_64`, `zfetch-rpm-portable-aarch64`
- `zfetch-musl-x86_64`, `zfetch-musl-aarch64`
- `zfetch-arch-x86_64`

Validate downloaded SHA256SUMS files for each artifact, then run `.deb` on a
Debian 12/Ubuntu 22.04 test environment, `.rpm` on Rocky 9/Fedora, native Arch
package on Arch, and static tarball on older systems. CI smoke tests on build
containers are helpful but do not replace independent distribution testing.

## Update manager limitation

The existing `zfetch --update` is **Debian/DPKG-oriented and x86_64-only**.
`zfetch --check-update` remains available as a read-only update check.
For RPM, Arch, ARM64 and tarball distributions, use the package manager or
manually download the correct file. Do not overwrite binaries managed by
another package manager with `zfetch --update`. Do not promise automatic
updating for those formats in release notes.

## Final release gate (separate Sprint 09)

Only after this sprint passes: bump `Cargo.toml` to 0.4.0, update `Cargo.lock`,
run 80+ unit tests and all CI workflows, check matching architecture/version
and checksums of ALL release assets, publish tag `v0.4.0` through the preferred
GitHub Desktop/GitHub UI flow, and attach release artifacts. Do not add AppImage.
